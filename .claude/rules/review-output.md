# 리뷰 / 보고 출력 룰

모든 review agent (code-reviewer-*, spec-reviewer-*) + debugger agent + 구현 agent (backend / frontend) + 메인 세션 공통. 리뷰·디버깅·작업 보고 결과 작성 시 본 룰 따른다.

## 메타 원칙 (Blocking)

> **리뷰는 작성자의 다음 행동을 결정 가능하게 만들어야 한다. 행동으로 이어지지 않는 지적은 쓰지 않는다.**

지적이 많아도 "뭘 해야 할지 모르겠다" 가 되면 리뷰 실패. 우선순위·등급보다 **다음 액션 명확성** 이 상위.

## 1. TL;DR 3줄 강제 (출력 최상단)

응답 맨 앞에 반드시 다음 3줄.

```
판정: <승인 | 보류 | 반려>
핵심 차단: <가장 중요한 차단 사유 1개 — 1문장>
다음 액션: <사용자가 즉시 할 1개 행동 — 1문장>
```

판정 없음 / 단순 보고면 "판정" → "결과" 로 치환 (예: "원인 식별 완료").

## 2. 각 지적 항목 = 4-파트 구조 (필수)

모든 finding / 결함 / 제안 항목 다음 4부 형식 강제.

```
### [등급] <짧은 제목>

- **문제**: <한 문장 현상 서술. 코드 식별자는 백틱으로 감싸되 첫 등장 시 1줄 역할 설명 동반>
- **영향**: <이대로 두면 어떤 버그 / 혼란 / 비용이 발생하는지>
- **근거**: <파일:라인 또는 spec 섹션 인용. 추측이면 "추측" 명시>
- **조치**: <어느 파일의 어느 섹션에 무엇을 추가 / 수정해야 하는지 구체 문장 또는 의사코드. "정책 명시 필요" 같은 요구사항 표현 금지 — 행동 동사 사용>
```

**조치 작성 룰**:
- "X 정책 명시 필요" ❌ → "tech-spec.md §3.2 에 `observation=null & score!=null` 분기 추가" ✅
- "검토 필요" ❌ → "InterviewService.startInterview() 의 락 범위 트랜잭션 전체로 확장" ✅

## 3. 식별자 첫 등장 룰 (필수)

클래스 / 함수 / 변수 / 파일명 / 설정 키 첫 등장 시 **반드시 1줄 역할 설명** 동반.

- ✅ `NonverbalRubricScorer` (비언어 응답에 루브릭을 적용해 점수를 산출하는 채점기)
- ✅ `_dimensions.yaml` (루브릭 차원 정의 파일 — composure / clarity 등 평가 축 목록)
- ❌ `NonverbalRubricScorer 의 composure 처리가...`

같은 문서 내 재등장 시 설명 생략 가능.

## 4. 약어 / jargon 금지 (또는 풀어쓰기)

다음 표기 그대로 사용 금지. 불가피 시 첫 등장 1문장 정의 동반.

- `[결함 skip]` → "결함 발견 시 해당 행 적재 안 함 (skip 분기)"
- `orphan` → "본 변경으로 생긴 unused import / 변수 / 함수"
- `grep evidence` → "코드 grep 으로 확인한 근거"
- `path:line 30+` → "30개 이상 파일:라인 인용"

내부 용어 / 메모리 약어를 외부 독자에게 그대로 던지지 말 것.

## 5. 우선순위 등급 = "차단 사유 + 사용자 행동"

P0 / P1 / P2 (또는 동등) 부여 시 다음 2개 함께 명시.

- **왜 이 등급인가** (1문장 — 차단 사유 / 영향 범위 근거)
- **사용자가 다음에 할 행동** (1문장 — 구체 액션)

```
P0 — 차단 사유: 운영 5xx 직결. 다음 행동: tech-spec.md §3.2 분기 추가 후 재제출.
```

## 6. 사전 점검 (출력 직전 self-check)

출력 송신 전 자체 점검 1문항.

> "이 리뷰 / 보고를 처음 보는 동료가 코드를 열어보지 않고도 무슨 문제인지 이해할 수 있는가?"

답이 NO 인 항목은 다시 쓴다. 코드 알아야 읽히는 리뷰 = 실패.

## 7. 안티 패턴

다음 출력 = 룰 위반. 작성 직후 폐기 후 재작성.

- 컨텍스트 없는 고유명사 나열 ("`NonverbalRubricScorer` 의 `composure` 가...").
- 4파트 중 "조치" 누락 또는 "정책 명시 필요" 같은 요구사항 표현.
- 식별자 첫 등장 시 역할 설명 누락.
- 우선순위만 있고 다음 행동 부재.
- TL;DR 3줄 부재 / 형식 위반.
- 압축 표기 (`[결함 skip]`, `orphan`, jargon) 풀이 없이 사용.

## 8. 적용 예시 (Good)

```
판정: 보류
핵심 차단: tech-spec §3.2 결함 분기에 observation=null 케이스 누락.
다음 액션: tech-spec.md §3.2 에 observation=null & score!=null 분기 명시 후 재제출.

---

### P0 — observation 필드 null 처리 방침 부재

- **문제**: LLM 이 점수 (`score`) 는 정상 반환하고 관찰 텍스트 (`observation`) 만 null 로 반환하는 경우의 분기가 spec 에 없음. `observation` = LLM 이 비언어 행동을 묘사하는 자연어 필드.
- **영향**: 구현자가 임의로 결정하게 되어 누구는 행을 버리고 누구는 빈 문자열로 저장 → 데이터 일관성 깨짐.
- **근거**: tech-spec.md §3.2 "결함 분기" 에 `score=null` 만 정의됨.
- **조치**: tech-spec.md §3.2 에 다음 분기 추가 — "`observation=null & score!=null` → (a) 행 자체를 적재하지 않음 / (b) `observation=""` 로 적재" 중 1개 선택해 명시.
```
